# Protocol and storage security review

This is a scoped source and regression review of the development bridge, not an independent penetration test or a production-security certification. Review work is tracked in [#15](https://github.com/Pratikkk/MacBridge/issues/15). No live keys, pairing secrets, notification contents or private device identifiers were used in regression fixtures.

## Threat model and boundaries

| Actor / input | Required boundary | Reviewed controls and limitations |
| --- | --- | --- |
| Unpaired LAN client | Cannot gain sharing access | TLS 1.2+, a fresh signed P-256 challenge, separate 256-bit five-minute single-use pairing secret, stored phone public key, four concurrent Mac connection slots and socket timeouts. LAN presence and Bonjour are not authorization. A deliberate availability attack remains possible. |
| Forged discovery or changed Mac identity | Cannot replace the pinned peer | Discovery checks saved ID/pin hints; the connection verifies the original SHA-256 SPKI pin, saved public key and certificate validity. Authentication transcript includes nonce and both identities. |
| Authenticated peer with hostile frames | Cannot overrun parsing, coerce typed fields or escape transfer storage | 1 MiB byte limit before network parsing, strict JSON syntax, maximum 32 container levels, duplicate-key and non-finite-number rejection. Android rejects string/boolean/integer coercion. Files use bounded sizes/chunks, sequential offsets, SHA-256, private snapshots and sanitized/generated destination names. Total retained storage and sustained valid-message work still need quotas. |
| Replayed transfer or notification action | Cannot target another identity/session or execute twice | Transfer checkpoints bind both public identities and expire after ten minutes; resume verifies partial/snapshot hashes. Notification handles bind live generation, app, peer and session, remain in memory, and are consumed once. Disconnect, revocation and preview changes invalidate work. |
| Revoked permissions or locked phone | Cannot continue unauthorized sharing/actions | Android rechecks stored peer permissions and identity; listener access and selected-app consent are required. Reply additionally requires previews and an unlocked phone. Source-app capability, generation and clearability are rechecked. Android has no atomic generation-check-and-send/cancel primitive, so a narrow platform race remains. API acceptance does not prove message delivery. |
| Corrupt persisted state or missing private key | Cannot silently change a paired identity | Checkpoint size/depth/shape/hash/identity checks discard invalid recovery state. Android production has no software-key fallback and now refuses to recreate a missing key when identity metadata exists. An explicit Android recovery screen now offers safe retry and a journaled, confirmed reset while preserving verified files; see [recovery behavior](android-identity-recovery.md). |
| Another OS user | Cannot read ordinary private state | Android app-private files/Keystore, backup exclusion and permission-protected exported services; Mac owner-only public state files and non-synchronizing login Keychain storage for the native app’s private identity. The separately delivered Keychain feature (#14) preserves the existing identity and fails closed on missing or denied access. Legacy standalone CLI identities still use file-backed keys; the Python TLS engine needs the native identity in process memory. |

A compromised app process, rooted phone, administrator or malicious program running as the same Mac user can defeat this development build's assumptions. The Mac app is not sandboxed or notarized; its Python interpreter/engine and OpenSSL are part of the trusted computing base. Clipboard history, verified received files and transfer metadata persist locally; they are not individually encrypted by the bridge. Notification bodies and action capabilities are not persisted by the relay. The Google Play services scanner can download a module and depends on Google infrastructure; direct bridge connections use no relay.

## Findings fixed in this change

| Finding | Evidence / repair | Regression coverage |
| --- | --- | --- |
| Parser errors could disclose peer content in Android diagnostics | `JSONObject` error messages contain the supplied document. `ProtocolCodec` previously logged `exception.message`; it now logs only the exception class and a fixed diagnostic. | A malformed synthetic clipboard/secret fixture proves the platform error contains the fixture, then verifies it appears in neither diagnostic history nor Logcat. |
| Byte bounds did not limit JSON nesting or resolve duplicate fields | Android's permissive JSON parser accepted coerced scalars and ambiguous syntax. Both network readers now reject duplicate fields/non-finite numbers and cap container depth before recursive object parsing. Authentication challenge/ACK and transfer-checkpoint readers use the same boundaries. Unknown extension fields remain permitted within those bounds. | Deep sub-limit documents, duplicates at nested levels, trailing documents, comments/unquoted syntax, fractional/overflow numeric fields, string booleans, null strings and healthy Unicode/escaped quotes/brackets; every current Android message round-trips. |
| A lost Android Keystore alias could silently rotate an existing identity | `ensureIdentityKeyExists` generated a replacement for a missing alias even with a saved device ID. It now requires explicit recovery instead; no device-ID changes or software fallback occur. | Inject an empty test Keystore with existing synthetic device metadata and verify startup fails, metadata remains unchanged and no key/fallback is written. A real phone key was not deleted or revoked. |
| Unused cloud SDK startup was included in a local bridge | Firebase AI/App Check and the Google Services app plugin were inherited without any application call sites. Removed those active dependencies/plugin and the unused Secrets app plugin, so local `.env` keys have no packaging path through that template plugin. ML Kit's required component registrars remain for code scanning. | Runtime class/BuildConfig checks and merged-APK manifest inspection verify Firebase initialization/App Check components are absent; Google scanner support remains declared. This is not a claim that all dependencies make zero network requests. |

## Validation and remaining acceptance

Run `./gradlew :app:assembleDebug :app:testDebugUnitTest`, `python3 -m unittest discover -s mac -v`, `mac/native/test-app.sh`, and `mac/native/build-app.sh`, followed by strict bundle signature verification. Android interoperability tests run actual pinned TLS against an isolated Python peer. Existing suites cover expired/reused pairing codes, signature replay, identity changes, reconnects, both file directions, path traversal, malformed/oversized chunks, corrupt/expired checkpoints, permission revocation, notification generations and orderly shutdown. New checks are in `SecurityReviewTest.kt` and `mac/test_security_review.py`. The issue's delivery comment records exact executed results and installation outcome.

The original review was validated against its isolated source snapshot, excluding the then-unfinished Keychain work and IDE state. The subsequent Keychain feature (#14) passed its own automated checks and installed startup, restart and existing-phone reconnection checks; its issue records those results. This does not extend the original review into an independent Keychain security assessment.

Open work remains:

- [#30: cumulative resource bounds](https://github.com/Pratikkk/MacBridge/issues/30). Per-frame/per-file limits do not provide a history/storage quota or sustained-message budget for a consenting authenticated peer.
- [#13: native Swift transport](https://github.com/Pratikkk/MacBridge/issues/13), and [#16: signed/notarized distribution](https://github.com/Pratikkk/MacBridge/issues/16).
- [#24: physical notification acceptance](https://github.com/Pratikkk/MacBridge/issues/24) and [#27: installed login/update acceptance](https://github.com/Pratikkk/MacBridge/issues/27). Automated checks do not establish actual system permission/banner behavior or login/update trust.

This pass did not fuzz every parser, benchmark sustained abuse, independently audit dependencies/cryptographic implementations, simulate compromised OS accounts, or perform a public-release assessment. Open follow-ups prevent blanket release-readiness/security claims; the milestone remains open.

Same-key Mac certificate renewal (#29) is separately validated and documented in [certificate renewal](certificate-renewal.md). Android still rejects invalid dates and changed pins.
